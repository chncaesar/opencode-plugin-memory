# DESIGN — PR-gated project memory

Design intent for the next version of `opencode-plugin-memory`. This file describes
specification and structure only; it contains no code.

## Problem

The current plugin gives one user persistent memory in a single local file
(`.opencode/memory/MEMORY.md`). Two limitations make it unfit for a team:

- The single file causes merge conflicts and coarse diffs when several people edit it.
- Memory is written autonomously by the model with no human review, so a wrong or
  harmful memory silently becomes shared truth.

This design moves memory behind the same gate as code: a pull request. A memory is not
valid until a human merges it.

## Principles

- **Single source of truth is git.** The repository holds the canonical memory store.
- **A memory is valid only after merge.** Nothing proposed is trusted before a human
  approves it.
- **Credential-free agent.** The agent never holds repository credentials and never runs
  git. It only writes a local file.
- **Progressive context loading is preserved.** The prompt sees a compact index of
  titles; full bodies are loaded lazily on demand.
- **Memory validity is independent of code reversibility.** A memory survives its own
  review lifecycle; it is never bundled into a code change, so reverting code never
  silently falsifies a memory.

## Scope

Memory is project-scoped only for now. There is no personal store and no team/org
namespace.

## Physical layout

```
.memory/staging/mem-*.md    machine-local drop folder, git-ignored, agent writes here
memory/active/mem-*.md      merged truth; the only memories injected into context
memory/retired/mem-*.md     removed memories, with reason and provenance
memory/_summary.md          committed index, one line per active memory, regenerated by CI
```

State is positional: the folder a file lives in is its status. Provenance and identity
live in YAML frontmatter on each file, so a file is self-describing even when moved
between folders.

### Frontmatter fields

- `id` — short random identifier, collision-free (never a sequential counter).
- `title` — the one-line title shown in the index.
- `author` — the human whose session proposed the memory.
- `source` — free text describing the session or change that produced it.
- `proposed_at`, `approved_at`, `approved_by` — lifecycle timestamps and actors.
- `supersedes` / `superseded_by` — forward and back links between replaced memories.
- `retired_at`, `retired_reason` — retirement timestamp and a reason from a fixed
  vocabulary: `wrong`, `stale`, `useless`, `superseded`, `duplicate`.
- `related_pr` — optional link to the code change that motivated a change-tied memory,
  for provenance only (never bundling).

### Identity

IDs are random and collision-free. This is required because multiple branches may add
memories concurrently; a sequential counter (`nextSeq`) would allocate the same ID on two
branches. The sequential scheme is retained only inside the migration path.

## Lifecycle

```
detect → propose → bot opens PR → human approves (merge) → CI regenerates index → live
```

1. **Detect.** The agent notices a durable fact. It checks staging and `active/` to avoid
   proposing a duplicate.
2. **Propose.** The agent writes `mem-<id>.md` to `.memory/staging/`. Nothing else. The
   file carries its own provenance in frontmatter.
3. **Bot.** The bot detects the staged file, branches, commits it into `memory/active/`,
   opens a dedicated memory PR, and removes the staged file.
4. **Review.** A human reviews against the memory checklist and merges. Merge is the only
   approval; there is no separate promotion step.
5. **Live.** On merge, CI regenerates `_summary.md` from `active/`. The memory is now
   injected into every session.
6. **Supersede.** A new memory replaces an old one through the same PR path: the new file
   lists `supersedes`, and the same PR moves the old file to `retired/` with
   `superseded_by`. Removal is therefore reviewable in the diff.
7. **Retire.** A memory moves to `retired/` with a `retired_reason`, through a PR, when it
   is wrong, stale, or useless. No automatic aging deletes anything.
8. **Audit.** A read-only background check proposes retirement or supersession PRs. It
   never edits `active/` directly.

## Read path

Reads come from the working tree, and only `active/` is valid. `retired/` and staging are
never injected.

- **Context injection.** Each session injects the committed `_summary.md` index (one line
  per active memory) plus the fixed writing policy. The model sees titles and IDs, not
  full bodies.
- **On-demand read.** `memory_read <id or keyword>` opens `memory/active/mem-*.md`. Full
  bodies are loaded only when requested.
- **`memory_review`.** Read-only view over the active store: aging entries, audit-flagged
  entries, and open memory PRs listed as "pending decisions". It never edits anything.
- **Staleness is accepted.** The index is committed to the branch, so a session sees the
  active set as of the branch's last rebase or merge. Memories merged after the branch
  diverged are invisible until rebase or merge. The runtime never reads the default
  branch.
- **Staged proposals are visible to their own author only.** The proposing agent may read
  its own staging folder back to avoid proposing a duplicate within the session. Staging
  is machine-local and invisible to everyone else.

## Write path

The agent never writes to `active/`, `retired/`, or `_summary.md`. It only ever writes a
proposal file into staging. Every mutation becomes a proposal.

A staging file carries an `intent` field in its frontmatter, telling the bot what to do:

- `intent: propose` (default) — a new memory, optionally with `supersedes: [old-id]`.
- `intent: retire` — remove an existing active memory; the file names the target `id` and
  a `retired_reason`, and has no body.

- **`memory_propose`** writes `mem-<id>.md` to `.memory/staging/`, after duplicate check,
  secret scan, and granularity/title-coherence validation.
- **`memory_update`** does not edit `active/`. It proposes a new memory that carries
  `supersedes: [old-id]`.
- **`memory_delete`** does not edit `active/`. It proposes a retirement: a staging file with
  `intent: retire` that moves `active/old-id` to `retired/` with a `retired_reason`.
- **The bot** branches on `intent`: `propose` commits the file into `active/` (and, when it
  carries `supersedes`, moves the old file to `retired/` in the same diff); `retire` moves
  `active/<id>` to `retired/` with the reason. Either way it opens the PR and removes the
  staged file.
- **CI** regenerates `_summary.md` on merge. Proposing never touches the index, which
  keeps proposed memories invisible until merged.

## Audit path

The audit is a read-only proposal source, identical in mechanism to the agent but with a
different trigger and remit:

- Trigger: runs in the background after a session goes idle.
- Scope: reads `active/` only; never edits `active/` or `_summary.md`.
- Detects contradiction, duplication, refinement, and staleness.
- Emits a proposal to staging (retirement or supersession), which the bot turns into a PR.
- `review.json` no longer exists; the PR is the durable record of a suggestion and its
  outcome.

## Roles

- **Agent** — proposes only, by writing a local file. No credentials, no git, no direct
  edit to shared truth.
- **Bot** — watches staging, branches, commits, opens PRs. Holds the only repository
  credentials.
- **Human** — approves merges. This is the entire trust model.
- **CI** — regenerates the committed index on merge.
- **Audit** — read-only; suggests retirement and supersession via PRs.

## Memory checklist (review gate)

A memory PR is accepted only when the memory is:

- **True** — correct today.
- **Relevant** — points at something that still exists in the codebase.
- **Useful** — a future session would waste time re-learning it if absent.
- **Scoped** — one entry, one rule; no bundling unrelated facts.
- **Clean** — no secrets, no customer data, no credentials.
- **Not a duplicate** — checked against active and proposed memories.

## Failure handling

- **Secret scan** rejects a proposal containing credential patterns before it reaches
  staging, naming the secret type and never echoing the value.
- **Unwritable staging** surfaces as a clean "not writable" message, never a raw I/O
  error.
- **Bot down** — proposals accumulate in staging; the agent avoids duplicates by checking
  staging before proposing. Soft degradation, no data loss.
- **Bot crash mid-run** — the bot is idempotent: a file already promoted is gone from
  staging, so re-running sees nothing and does not double-commit.
- **Open-PR failure** — the bot leaves the staged file, logs, and retries on the next
  poll; it never spins.
- **Duplicate proposals** — two sessions propose the same fact; the reviewer or the audit
  resolves the duplicate. Same behavior as today, only more visible.

## Migration from the current single-file store

The existing `.opencode/memory/MEMORY.md` (Active/Archived sections, `MEM-NNN` IDs,
`nextSeq` counter) converts to one-file-per-memory:

- Each Active entry becomes `active/mem-<random>.md`, body preserved, `author: unknown`,
  `source: "migrated from legacy MEMORY.md"`, with `proposed_at`/`approved_at` derived
  from the entry's `added`/`updated` dates.
- Each Archived entry becomes `retired/mem-<random>.md`, with `retired_reason` mapped from
  `archived_reason`, and `superseded_by` re-linked to the new ID of the replacement.
- A sidecar mapping (old ID → new ID) is preserved so `superseded_by` references resolve.
- Migration is idempotent and triggered at plugin startup. The legacy `MEMORY.md` is left
  in place as a backup and never deleted.

## Bot and CI form

- **Bot** — a local daemon or CLI running on the developer's machine. It watches the
  git-ignored `.memory/staging/` folder and opens PRs via `gh` or the GitHub API, holding
  the only repository token. It cannot be a GitHub Action, because a GitHub Action runs on
  the remote and can never see a local, git-ignored staging folder.
- **CI** — a GitHub Action that runs on merge to the default branch and regenerates the
  committed `_summary.md`. This is correctly an Action because it runs remotely after
  merge.

## Open decisions

Resolved at implementation:

- **Staging folder name** — `.memory/staging/` (machine-local and hidden).
- **Bot form** — a local CLI/daemon (`opencode-memory-bot`), invoked as
  `once` (process staging and exit), `watch` (poll staging on an interval), or
  `regenerate` (rebuild the index; used by CI). It uses the `gh` CLI, already
  authenticated on the developer machine, to open PRs.
- **PR title/body template** — title `memory: <title>` for proposals and
  `memory: retire <id>` for retirements; body carries ID, title, author, intent
  (and supersedes/reason when present) plus the memory checklist.
- **Bot retry policy** — the bot is idempotent: a proposal whose branch already
  exists is skipped; a failed PR open leaves the staged file in place for the
  next poll (it never spins). A crash after promotion leaves the working tree
  changed but never double-commits.
- **Audit form** — the audit is model-judged, not age-based. After a session
  goes idle, a restricted `memory-audit` agent (no tools, `small_model`) reads
  every active memory and reports duplicate / refinement / contradiction
  findings. Each finding becomes an `intent: retire` proposal (with
  `superseded_by` for refinements), which the bot turns into a PR. Staleness is
  only the informational "aging" list in `memory_review`; nothing is retired on
  an age threshold.
